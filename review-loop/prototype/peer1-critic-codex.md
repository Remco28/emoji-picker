## Verdict

**No, not reliably as written.** The measured probe shows that IBus can accept a commit on its internal fake context and silently drop it. The plan’s focus-generation and 60 ms stability checks still allow that outcome: for example, the picker hides, the fake context gets focus, the target app takes longer than 60 ms to regain focus, and no cursor-location update arrives during that interval. The engine can report the commit as accepted even though the emoji never reaches the app.

That failure follows from a behavior measured in [PROBLEM.md](/home/frank/.cache/emoji-picker-review/plan-r1/critic/plan/PROBLEM.md) and a race in the planned insertion logic. **The specific timing scenario is an inference**; it hasn’t been measured on Frank’s machine. The plan also doesn’t make automatic paste its fallback: when IBus is unavailable or times out, it copies the emoji and asks Frank to paste it manually. That does not fulfill the stated “have it appear” goal in that case.

## Enrichment evaluation

**It could pass while search still feels poor.** The pass rule rewards expected emoji appearing somewhere in the top 5–12, but does not penalize irrelevant results occupying those slots. A query can pass while its chart is noisy or while the most useful emoji is buried. The noise-query requirement is also underspecified: “must not produce confident nonsense” has no defined confidence threshold or scoring rule.

Writing the answer key before generating enrichment is a useful guard against direct fitting. The held-out set is still generated by another model, and reviewing it only for impossible expectations does not establish that the queries or expected rankings represent real searches. The current criteria also do not measure whether the concept rows, prefix behavior, or sentence search make the result easy to use.

The planned headless test has a related gap. It checks a **scripted** picker-to-fake-to-target focus sequence, but that does not establish that the timing and context sequence match GNOME on Frank’s Wayland session. The simulated sequence can pass while real insertion still hits the fake context.

## Contradictions with PROBLEM.md

I found no direct contradiction with Frank’s stated decisions: the plan uses an independent shortcut, keeps LLM work at build time, includes a large keyboard-navigable chart, and leaves replacing Super+. for later. It also avoids `ibus restart`, consistent with the measured breakage.

There is one gap between the goal and the stated fallback: copying and asking Frank to paste manually is not insertion into the app. That may be an acceptable degraded mode, but it should not count as the goal succeeding.

The claim that the fake context lacks a cursor-location update is **not established by the facts reported in PROBLEM.md**. It may have been observed in the probe, but I can’t verify that from the available report or logs.

## What I would cut

I would defer typo tolerance and the elaborate font-version cutoff. Neither is needed to prove the central flow, and both add ranking or detection logic that can mislead if it is wrong. Keep the requested semantic search, keyboard navigation, variants, recents, and frequency.

For the first working prototype, I would also simplify resident-app activation if Frank’s Wayland test shows the token path is unreliable. The probe’s fresh-process shortcut path is measured to open the picker; the resident D-Bus activation path is not. Keep the latter only after it passes the real Wayland test.
