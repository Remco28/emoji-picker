## Findings

1. **HIGH — Uninstalling one user’s install breaks every user’s install.** The component and application files are machine-wide, while input sources and shortcuts are per-user. For example, users A and B install with different layouts; A then runs the uninstall launcher. The plan removes the shared component and package unconditionally, so B’s converted sources can become unknown to IBus and the installed launcher disappears for B. The plan acknowledges the component affects other users, but warning them does not preserve their working setup or give them a clear recovery path. **I know** the component is shared and that GNOME skips unknown IBus sources; both are in the measured facts. This consequence follows from the plan’s uninstall steps.

2. **HIGH — A failed upgrade can leave the installed application unavailable.** The plan removes `/usr/local/lib/emoji-picker` before moving the staged directory into place. If the move or a later step fails, the old installation is already gone while the launcher and component still point at that path. An upgrade can therefore leave the user without either the old or new working install. **This is an inference** from the described `rm -rf`-then-`mv` sequence. Use versioned directories and an atomic symlink switch, or retain a rollback path.

3. **MEDIUM — Uninstall can delete a shortcut the user has since changed.** If the user changes the binding or command but leaves the name “Emoji Picker,” the plan still removes the shortcut based on its name alone. That loses a user edit without warning. **This follows directly from the plan.** On uninstall, check that the command and binding still match the values this install wrote; otherwise leave the shortcut and explain why.

4. **MEDIUM — Setup deliberately has a period where Super+. opens a picker that may only copy.** On a fresh install with a running IBus daemon that has not loaded the new component, the plan changes the shortcut and removes IBus’s Super+. hotkey immediately, but leaves input sources unchanged until a later login. During that interval the picker can open, while Enter may copy instead of inserting. This is stated in the plan, so it is not a hidden failure, but the “one password prompt” flow should make that interim behavior plain. A slow IBus startup can extend it; the plan’s 60-second retry then leaves setup pending for another login. **I know** the daemon does not load the new component until restart/login and that the picker has a copy fallback; the timing and user experience described here follow from those facts and the plan.

5. **LOW — Keeping removed layout engines forever is unnecessary accumulation.** The plan retains every previously installed `emoji-picker:*` engine to protect other users. That does protect their current sources, but also keeps engines for layouts no user may still need. This is not a meaningful user harm by itself; it adds complexity to global ownership and cleanup. **This is an inference** from the retention rule. Track which users need the shared component, or document that stale engine entries are expected.

## Design decisions and behavior

- **Per-layout engine names and IBus attributes — LOW / verify before release.** IBus components support layout, variant, language, symbol, and long name metadata; the plan’s basic use of those attributes is plausible. The supplied measured facts establish that IBus needs a non-empty `layout_variant` only when there is a variant. I **believe** names such as `emoji-picker:de+nodeadkeys` are accepted, but I could not verify that against IBus 1.5.34 here. Keep the planned private-daemon test for the exact generated component and engine names.

- **Replacing XKB sources with IBus sources — MEDIUM.** With one source, the measured GNOME behavior says the indicator hides. With two layouts—or a layout plus Japanese—there are still multiple sources, so the indicator remains. That is consistent with the owner’s goal that the tool not add an indicator when there was only one source; it does not make the indicator disappear for users who already need a source menu. For an existing Japanese IBus source, the picker also cannot insert while Japanese is active; the stated copy fallback still applies. **These behaviors are known from PROBLEM.md.**

- **Custom Super+. binding and IBus hotkey — MEDIUM.** Removing only `<Super>period` while preserving `<Super>semicolon` matches the stated ownership goal. However, the plan’s collision warning only covers settings it scans; it cannot establish that no other software or hard-coded GNOME behavior uses the chord. I **believe** GNOME custom media-key bindings accept `<Super>period`, but this plan has no target-machine check for the exact binding on GNOME 50. The Wayland human-feedback round is useful, but should include checking that the built-in picker no longer reacts and the new picker does.

- **No-XKB setup — MEDIUM.** If a user has no XKB source, the plan leaves their sources alone and says insertion will copy. That avoids inventing a keyboard layout, but means they do not get IBus insertion through this tool. The plan should state this as a supported limitation in the installer output and README. **This follows from the plan.**

- **`/usr/local` placement — no finding.** Installing the application under `/usr/local` and the IBus component under `/usr/share/ibus/component` is consistent with the measured IBus search paths and the need for a machine-wide component. I **know** the component path is required for this target from PROBLEM.md. The consequential concern is shared ownership and removal, above.

## Can it leave the system worse?

Yes. The clearest case is one user uninstalling the machine-wide component and files while another user still has converted sources or relies on the installed launcher. A failed directory replacement during upgrade can also remove the working application before the replacement is in place. The per-user source conversion has a safe pending state during slow IBus startup—the plan leaves those sources alone until the engines appear—but that state temporarily changes Super+. behavior.

## What I would cut

I would cut the desktop-app-grid entry unless opening the picker from the app grid is a real requirement; it does not advance the install, upgrade, uninstall, shortcut, or indicator goals. I would also cut the attempt to preserve unknown prior `emoji-picker:*` engines until there is a defined multi-user ownership and uninstall model. The current preservation rule creates a global shared component, but the uninstall plan still removes it globally.

I read the plan, measured facts, and relevant prototype scripts. I did not run tests or validate behavior on Ubuntu 26.04/GNOME 50/IBus 1.5.34, so the exact custom-binding behavior and colon/plus engine-name acceptance remain unverified.
